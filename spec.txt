TPT Archon: Design Document
Executive Summary
TPT Archon is a vertically integrated, proof-native computing stack that eliminates the boundaries between storage, operating system, and database. Built from the inside-out using Rust's ownership model and formal verification, Archon achieves theoretical maximum performance by unifying the page cache, kernel memory management, and database buffer pool into a single, zero-copy address space.
Core Innovation: Unlike legacy stacks (Linux + PostgreSQL + SQLite) that suffer from 30-40% CPU overhead due to middleware boundaries and double-buffering, Archon treats the storage engine, microkernel, and relational database as a single, mathematically verified continuum.
Architecture Overview
The Inside-Out Strategy
Archon is built in three phases, each layer designed to perfectly accommodate the next:
Phase 1: tpt-archon-core - The atomic, no_std, zero-allocation storage engine
Phase 2: tpt-archon-kernel - The capability-based microkernel with unified page cache
Phase 3: tpt-archon-relational - The AI-native, GPU-accelerated query engine
The key insight: we build the OS before the database so the database can be natively compiled for it, but we build the storage engine first so the kernel's memory manager is designed around the storage engine's page model.

Crate Specifications
1. tpt-archon-core (The Atom)
Purpose: A #![no_std], zero-allocation, single-file storage engine that provides mathematically verified crash-safety and concurrent access.
Key Components:
Block Device Abstraction

pub trait BlockDevice {
    const BLOCK_SIZE: usize = 4096; // 4KB pages
    
    fn read_block(&self, block_id: BlockId, buffer: &mut [u8]) -> Result<(), StorageError>;
    fn write_block(&mut self, block_id: BlockId, data: &[u8]) -> Result<(), StorageError>;
    fn sync(&mut self) -> Result<(), StorageError>;
}

Design Decisions:
Uses tpt-zero-bytes for zero-allocation I/O operations
Supports multiple backends: NVMe, memory-mapped files, in-memory (for testing)
All operations return Result with detailed error types
Page Manager & Buffer Pool
Divides block device into fixed-size pages (4KB or 16KB)
Tracks page states: Free, Clean, Dirty, Pinned
Implements LRU eviction with dirty-page writeback
Critical: Designed so the kernel can map these pages directly into user-space (unified page cache)
Write-Ahead Log (WAL)
Append-only log for crash recovery
Every page modification is written to WAL before the main storage
Uses Log Sequence Numbers (LSN) for ordering
Formal Verification: tpt-telos proves the invariant: Replaying the WAL after any crash results in a consistent state
B-Link Tree
Concurrent B-Tree variant allowing latch-free reads
Structural invariants enforced at compile-time via tpt-eidos
Node capacity checked at type level (cannot overflow page size)
Supports range scans, point lookups, and concurrent inserts
Dependencies:
tpt-zero-bytes (zero-allocation primitives)
tpt-eidos (dependently typed invariants)
tpt-telos (formal verification of WAL and B-Tree)
2. tpt-archon-bridge (The Glue)
Purpose: Provides the zero-copy IPC and unified memory management layer that connects the storage engine to the kernel and database.
Key Components:
Capability-Based IPC
Messages are strongly typed capabilities (not raw file descriptors)
A capability grants specific access rights (read page X, write to channel Y)
Capabilities are unforgeable and revocable
Implemented using tpt-eidos for type-level security
Unified Page Cache Traits
Defines the interface for sharing pages between kernel and storage
Allows the kernel to map storage pages directly into database address space
Eliminates double-buffering (no copying between kernel page cache and DB buffer pool)
Dependencies:
tpt-archon-core
tpt-eidos
3. tpt-archon-kernel (The Ruler)
Purpose: A capability-based microkernel that provides secure, zero-copy IPC and unified memory management.
Key Components:
Async Task Scheduler
Replaces process-per-connection with lightweight async tasks
Each database connection is a Rust Task, not an OS process
Uses io_uring for asynchronous I/O on Linux (when running as user-space)
Formal Verification: tpt-telos proves the scheduler cannot deadlock
Memory Management
Unified Page Cache: The kernel's page cache and the database's buffer pool are the same thing
Memory-mapped files with zero-copy access
Capability-based access control (tasks can only access pages they have capabilities for)
IPC Message Passing
Microkernel handles only IPC, scheduling, and memory management
Filesystems, network stacks, and drivers run in user-space as isolated services
Messages are capability-bearing, ensuring secure resource access
User-Space Driver Framework
Hardware drivers run in user-space for isolation
Kernel translates hardware interrupts into safe IPC messages
Drivers are written in safe Rust with minimal unsafe blocks
Dependencies:
tpt-archon-core
tpt-archon-bridge
tpt-eidos
tpt-telos
4. tpt-archon-relational (The Application)
Purpose: An AI-native, GPU-accelerated relational database engine that runs as a user-space service on the Archon microkernel.
Key Components:
SQL Parser
Hand-written, zero-allocation parser using tpt-zero-bytes
Supports PostgreSQL-compatible SQL dialect
Extensible for custom types and operators
Query Planner & Optimizer
Cost-based optimizer with statistics collection
AI-Native: Uses tpt-telos to generate and verify execution plans
Supports vectorized execution for analytical workloads
Execution Engine
Vectorized query execution (processes batches of rows, not single rows)
GPU Acceleration: Integrates tpt-gpu for:
Vector similarity search (for AI workloads)
Complex aggregations
Machine learning UDFs
Pushes compute down to GPU when beneficial
MVCC (Multi-Version Concurrency Control)
Implements Serializable isolation level
Uses the unified page cache from tpt-archon-bridge
Formal Verification: tpt-telos proves MVCC cannot violate serializability
Storage Integration
Uses tpt-archon-core for all persistence
No separate buffer pool (uses unified page cache)
Zero-copy access to storage pages
Dependencies:
tpt-archon-core
tpt-archon-bridge
tpt-archon-kernel
tpt-gpu
tpt-eidos
tpt-telos

Performance Advantages
Eliminating the Middleware Tax
Legacy stacks suffer from multiple layers of data copying:
Disk → Kernel Page Cache (OS read)
Kernel Page Cache → Database Buffer Pool (DB read)
Database Buffer Pool → Query Executor (in-DB copy)
Query Executor → Network Socket (response)
Archon's Solution:
Unified page cache eliminates steps 1-2 (kernel and DB share the same cache)
Zero-copy IPC eliminates step 3 (capabilities grant direct memory access)
Direct network integration eliminates step 4
Expected Performance Gain: 30-40% reduction in CPU overhead for I/O-bound workloads.
Zero-Allocation Critical Paths
By using tpt-zero-bytes and #![no_std] in the core, Archon eliminates:
Garbage collection pauses (no GC in Rust, but also no allocator overhead)
Memory fragmentation
Allocation-related latency spikes
GPU-Native Execution
Unlike PostgreSQL (which requires extensions like pgvector) or SQLite (which has no GPU support), Archon natively integrates tpt-gpu for:
Vector similarity search (for RAG, embeddings)
Complex analytical queries
Machine learning inference
Formal Verification Strategy
What We Verify
Storage Layer (tpt-archon-core):
WAL replay produces consistent state after any crash
B-Tree operations maintain structural invariants
Page allocation is free of use-after-free and double-free
Kernel Layer (tpt-archon-kernel):
Scheduler is deadlock-free
IPC message passing is free of data races
Capability system prevents unauthorized access
Relational Layer (tpt-archon-relational):
MVCC maintains serializability under all concurrency patterns
Query optimizer produces correct execution plans
GPU operations are memory-safe
How We Verify
tpt-telos: Generates formal proofs in Coq/Lean for critical algorithms
tpt-eidos: Enforces invariants at compile-time via dependent types
tpt-formal-lab: Provides the verification framework and proof automation
Verification as a Moat
Legacy databases rely on thousands of unit tests and fuzzing to find bugs. Archon uses mathematical proof to guarantee correctness. This is a fundamental competitive advantage that cannot be easily replicated by C/C++ codebases.

Risk Mitigation
Risk 1: Microkernel Complexity
Mitigation: Start with a user-space implementation (running on Linux) before attempting bare-metal. This allows us to validate the architecture without writing hardware drivers.
Risk 2: SQL Compatibility
Mitigation: Focus on PostgreSQL compatibility first (most widely used). SQLite compatibility can be added later as a separate compatibility layer.
Risk 3: Formal Verification Overhead
Mitigation: Only verify critical invariants (WAL, MVCC, scheduler). Use tpt-eidos for compile-time checks where possible (cheaper than full formal verification).
Conclusion
TPT Archon is not just a rewrite of Linux, SQLite, and PostgreSQL in Rust. It is a fundamentally new computing stack that eliminates the boundaries between storage, OS, and database.
By building inside-out, leveraging formal verification, and integrating GPU acceleration natively, Archon achieves performance and correctness that legacy C/C++ stacks cannot match.
The key insight: You don't need to rewrite the entire stack at once. Start with the atomic storage engine (tpt-archon-core), and let the kernel and database naturally wrap around it.
